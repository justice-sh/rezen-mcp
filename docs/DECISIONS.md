# Decision Log

Short records of decisions that shape the project. New decisions get the next number. A decision is never deleted: if it changes, add a new entry and mark the old one **Superseded**.

---

## ADR-001: Synthetic data only

- **Status:** Accepted (2026-11-20)
- **Context:** The project is inspired by real school report-card workflows, and the repository is public.
- **Decision:** All data is generated by a deterministic script. No real student, school or staff data is ever stored in the repo, issues, commits, or prompts.
- **Consequences:** Reproducible tests and evals; zero privacy risk from the repo. Real-world edge cases must be modelled deliberately (missing scores, ties) rather than discovered.

## ADR-002: MCP TypeScript SDK 1.x line

- **Status:** Accepted (2026-11-20)
- **Context:** Before building, we checked the npm registry: the `latest` tag of `@modelcontextprotocol/sdk` is a 1.x release.
- **Decision:** Use `@modelcontextprotocol/sdk` 1.x with `McpServer`, `registerTool`, and Zod schemas.
- **Consequences:** Stable, well-documented API. Revisit if a newer major line becomes the default; migration would be recorded in a new ADR.

## ADR-003: Read-only tools in v1

- **Status:** Accepted (2026-11-20)
- **Context:** Write tools raise consent, audit and safety questions that would dominate the project.
- **Decision:** All v1 tools are read-only and annotated `readOnlyHint: true`.
- **Consequences:** Smaller attack surface and simpler evals. A single guarded write tool may be reconsidered after Phase 4.

## ADR-004: Repository interface, in-memory first

- **Status:** Accepted (2026-11-20)
- **Context:** We want tools and evals working before introducing a database.
- **Decision:** Tools depend on a `Repository` interface. Phase 0 to 1 use an in-memory implementation; Phase 2 adds a Postgres implementation that must pass the same contract tests.
- **Consequences:** Fast tests now, a clean swap later. Risk: the interface is shaped by in-memory convenience. Mitigated by contract tests against both implementations in Phase 2.

## ADR-005: Strict TypeScript, Vitest, ESLint, Node 22

- **Status:** Accepted (2026-11-20); the Node version part is superseded by ADR-008
- **Decision:** `strict` plus `noUncheckedIndexedAccess`; Vitest for tests (including tests through a real in-memory MCP client); ESLint with typescript-eslint; Node 22 in CI and `.nvmrc`, with `engines` set to Node 20+. TypeScript is pinned to the 5.x line for a conservative toolchain.
- **Consequences:** Early error detection and fast feedback. Revisit TypeScript major version when convenient.

## ADR-006: Spec-first, phase-based delivery with written AI rules

- **Status:** Accepted (2026-11-20)
- **Decision:** `docs/FEATURE_SPEC.md` leads; `docs/IMPLEMENTATION_PLAN.md` defines phases with exit criteria; `docs/AI_WORKFLOW.md` defines how AI assistance is used and reviewed.
- **Consequences:** Reviewable history of intent, not just code. Cost: docs must be kept in sync with changes.

## ADR-007: pnpm as the package manager

- **Status:** Accepted (2026-11-20)
- **Context:** The maintainer prefers pnpm. The initial scaffold used npm and was switched before the first commit.
- **Decision:** Use pnpm, with the version pinned in the `packageManager` field of `package.json` and the lockfile (`pnpm-lock.yaml`) committed. CI installs with `--frozen-lockfile`. Dependency install scripts are blocked by default; `pnpm-workspace.yaml` explicitly denies esbuild's build script (`allowBuilds`), since the package works without it.
- **Consequences:** Reproducible installs and an explicit record of which dependencies may run scripts. Any new dependency that needs a build script must be reviewed and approved deliberately.

## ADR-008: Node.js 26 (LTS)

- **Status:** Accepted (2026-11-20)
- **Context:** ADR-005 pinned Node 22. Node 22 is in maintenance and, as far as we know, reaches end of life in April 2027. Node 26 was scheduled to enter LTS in October 2026, has end of life in April 2029, and the full check passes on 26.13.1.
- **Decision:** Use Node 26 in CI (`node-version: 26`) and `.nvmrc`, require Node >=26 in `engines`, and track the matching `@types/node` major. Pin an exact major rather than `lts/*`, and review the version each October when a new LTS arrives.
- **Consequences:** A longer support window and the same runtime locally and in CI. Contributors on older Node versions must upgrade. Supersedes the Node 22 part of ADR-005.

## ADR-009: Missing scores leave a student unranked; term defaults to the current term

- **Status:** Accepted (2026-11-20)
- **Context:** The feature spec left two questions open: how to rank students with missing scores, and how `term` should work. Student results are termly and a school never operates without a term (the target market is Nigeria), so a result without a term is meaningless.
- **Decision:** A student with any missing score or score part has no total, average or position, and is reported as unranked with the missing subjects. Missing scores are never treated as zero. Every response states the term it used. A caller may omit `term`, which means the school's **current term** (the term in progress, from `Repository.getCurrentTerm()`), not the latest term that happens to have data. An unknown term is an error that lists the valid terms.
- **Consequences:** Rankings never silently reward or punish incomplete data, and assistants are told exactly what is missing. Omitting the term is safe at the start of a term, when no scores have been entered yet. The current term must be defined by the data source: a dataset field now, and a terms table with dates in Phase 2. A caller who wants a partial ranking would need a new tool or option, which is out of scope for v1.

## ADR-010: Grade bands are fixed in v1

- **Status:** Accepted (2026-11-20)
- **Context:** Schools may want different grade bands, but configuration adds storage, validation and authorization work.
- **Decision:** Grade bands are the fixed defaults in the feature spec (A 70 to 100 down to F 0 to 39). Per-school configurable bands are a later feature.
- **Consequences:** Simpler tools, tests and evals now. When bands become configurable, grading functions will need the bands passed in, and that change will get its own ADR.

## ADR-011: No write tool in v1; revisit after Phase 4

- **Status:** Accepted (2026-11-21)
- **Context:** Open question 4 asked whether a single write tool with explicit confirmation (for example, recording a score) is worth adding. Write tools need authorization, an audit trail, undo, concurrency handling and harder, state-changing evals, which would dominate a small project. ADR-003 already made v1 read-only.
- **Decision:** No write tool in v1. Finish and polish the read-only server first, then decide after Phase 4.
- **Consequences:** A smaller attack surface and simpler evals now. If a write tool is added later, it gets its own spec section, authorization design and ADR.

## ADR-012: MCP Inspector for manual inspection

- **Status:** Accepted (2026-11-22)
- **Context:** Tests exercise the server through a real MCP client, but there was no quick way for a person to try the tools, resource and prompt by hand. The official MCP Inspector gives a browser UI for that.
- **Decision:** Add `@modelcontextprotocol/inspector` as a dev dependency, pinned to an exact version, and a `pnpm inspector` script that runs the server from source with `tsx`. The Inspector's install script is explicitly disabled in `pnpm-workspace.yaml` (`allowBuilds`): it only installs client dependencies in a source checkout and does nothing when used as a dependency, and an unreviewed build script would otherwise fail `pnpm install` in CI.
- **Consequences:** Anyone can explore the server in a browser with one command. A new dev dependency tree to keep current. The version is pinned, so upgrades are deliberate. The Inspector is a manual tool and is not part of `pnpm check` or CI. Over stdio it runs locally and uses only synthetic data; remote HTTP inspection waits for Phase 4.

## ADR-013: Layered environment configuration, validated once

- **Status:** Accepted (2026-11-22)
- **Context:** Phase 2 adds a database URL, a way to choose between a local and a Docker Postgres, and later per-school tokens. These need one validated, typed place to read configuration, and an easy way to override values per environment (development, test, production) without copying every variable.
- **Decision:** `src/config` reads `.env`, then an optional `.env.<NODE_ENV>` that overrides it, then real environment variables, which always win. `NODE_ENV` comes from the real environment, defaults to `development`, and only selects the file. All variables are declared in one Zod schema (`src/config/schema.ts`) and validated together; a bad value fails with one message listing every problem and the files that were read. Empty values count as unset. `NODE_ENV` must be a plain name, because it becomes part of a file name. The loader uses Node's built-in `util.parseEnv` (no `dotenv` dependency), writes nothing to `process.env`, loads nothing at import time, and logs nothing (stdout carries the MCP protocol on stdio). `.env` files are never committed; `.env.example` documents them. CI and hosting platforms set variables directly. `pnpm test` sets `NODE_ENV=test` through `cross-env` so it also works on Windows.
- **Consequences:** Environment-specific files stay small. A deployment can override any file value without editing files. The behaviour is pure, so the tests inject the directory and environment. `util.parseEnv` is documented by Node but should be rechecked when the Node line changes. A new variable means one line in the schema.
