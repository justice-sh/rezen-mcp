# Decision Log

Short records of decisions that shape the project. New decisions get the next number. A decision is never deleted: if it changes, add a new entry and mark the old one **Superseded**.

---

## ADR-001: Synthetic data only

- **Status:** Accepted (2026-11-20)
- **Context:** The project is inspired by real school report-card workflows, and the repository is public.
- **Decision:** All data is generated by a deterministic script. No real student, school or staff data is ever stored in the repo, issues, commits, or prompts.
- **Consequences:** Reproducible tests and evals; zero privacy risk from the repo. Real-world edge cases must be modelled deliberately (missing scores, ties) rather than discovered.

## ADR-002: MCP TypeScript SDK 1.x line

- **Status:** Accepted (2026-11-20)
- **Context:** Before building, we checked the npm registry: the `latest` tag of `@modelcontextprotocol/sdk` is a 1.x release.
- **Decision:** Use `@modelcontextprotocol/sdk` 1.x with `McpServer`, `registerTool`, and Zod schemas.
- **Consequences:** Stable, well-documented API. Revisit if a newer major line becomes the default; migration would be recorded in a new ADR.

## ADR-003: Read-only tools in v1

- **Status:** Accepted (2026-11-20)
- **Context:** Write tools raise consent, audit and safety questions that would dominate the project.
- **Decision:** All v1 tools are read-only and annotated `readOnlyHint: true`.
- **Consequences:** Smaller attack surface and simpler evals. A single guarded write tool may be reconsidered after Phase 4.

## ADR-004: Repository interface, in-memory first

- **Status:** Accepted (2026-11-20)
- **Context:** We want tools and evals working before introducing a database.
- **Decision:** Tools depend on a `Repository` interface. Phase 0 to 1 use an in-memory implementation; Phase 2 adds a Postgres implementation that must pass the same contract tests.
- **Consequences:** Fast tests now, a clean swap later. Risk: the interface is shaped by in-memory convenience. Mitigated by contract tests against both implementations in Phase 2.

## ADR-005: Strict TypeScript, Vitest, ESLint, Node 22

- **Status:** Accepted (2026-11-20); the Node version part is superseded by ADR-008
- **Decision:** `strict` plus `noUncheckedIndexedAccess`; Vitest for tests (including tests through a real in-memory MCP client); ESLint with typescript-eslint; Node 22 in CI and `.nvmrc`, with `engines` set to Node 20+. TypeScript is pinned to the 5.x line for a conservative toolchain.
- **Consequences:** Early error detection and fast feedback. Revisit TypeScript major version when convenient.

## ADR-006: Spec-first, phase-based delivery with written AI rules

- **Status:** Accepted (2026-11-20)
- **Decision:** `docs/FEATURE_SPEC.md` leads; `docs/IMPLEMENTATION_PLAN.md` defines phases with exit criteria; `docs/AI_WORKFLOW.md` defines how AI assistance is used and reviewed.
- **Consequences:** Reviewable history of intent, not just code. Cost: docs must be kept in sync with changes.

## ADR-007: pnpm as the package manager

- **Status:** Accepted (2026-11-20)
- **Context:** The maintainer prefers pnpm. The initial scaffold used npm and was switched before the first commit.
- **Decision:** Use pnpm, with the version pinned in the `packageManager` field of `package.json` and the lockfile (`pnpm-lock.yaml`) committed. CI installs with `--frozen-lockfile`. Dependency install scripts are blocked by default; `pnpm-workspace.yaml` explicitly denies esbuild's build script (`allowBuilds`), since the package works without it.
- **Consequences:** Reproducible installs and an explicit record of which dependencies may run scripts. Any new dependency that needs a build script must be reviewed and approved deliberately.

## ADR-008: Node.js 26 (LTS)

- **Status:** Accepted (2026-11-20)
- **Context:** ADR-005 pinned Node 22. Node 22 is in maintenance and, as far as we know, reaches end of life in April 2027. Node 26 was scheduled to enter LTS in October 2026, has end of life in April 2029, and the full check passes on 26.13.1.
- **Decision:** Use Node 26 in CI (`node-version: 26`) and `.nvmrc`, require Node >=26 in `engines`, and track the matching `@types/node` major. Pin an exact major rather than `lts/*`, and review the version each October when a new LTS arrives.
- **Consequences:** A longer support window and the same runtime locally and in CI. Contributors on older Node versions must upgrade. Supersedes the Node 22 part of ADR-005.

## ADR-009: Missing scores leave a student unranked; term defaults to the current term

- **Status:** Accepted (2026-11-20)
- **Context:** The feature spec left two questions open: how to rank students with missing scores, and how `term` should work. Student results are termly and a school never operates without a term (the target market is Nigeria), so a result without a term is meaningless.
- **Decision:** A student with any missing score or score part has no total, average or position, and is reported as unranked with the missing subjects. Missing scores are never treated as zero. Every response states the term it used. A caller may omit `term`, which means the school's **current term** (the term in progress, from `Repository.getCurrentTerm()`), not the latest term that happens to have data. An unknown term is an error that lists the valid terms.
- **Consequences:** Rankings never silently reward or punish incomplete data, and assistants are told exactly what is missing. Omitting the term is safe at the start of a term, when no scores have been entered yet. The current term must be defined by the data source: a dataset field now, and a terms table with dates in Phase 2. A caller who wants a partial ranking would need a new tool or option, which is out of scope for v1.

## ADR-010: Grade bands are fixed in v1

- **Status:** Accepted (2026-11-20)
- **Context:** Schools may want different grade bands, but configuration adds storage, validation and authorization work.
- **Decision:** Grade bands are the fixed defaults in the feature spec (A 70 to 100 down to F 0 to 39). Per-school configurable bands are a later feature.
- **Consequences:** Simpler tools, tests and evals now. When bands become configurable, grading functions will need the bands passed in, and that change will get its own ADR.

## ADR-011: No write tool in v1; revisit after Phase 4

- **Status:** Accepted (2026-11-21)
- **Context:** Open question 4 asked whether a single write tool with explicit confirmation (for example, recording a score) is worth adding. Write tools need authorization, an audit trail, undo, concurrency handling and harder, state-changing evals, which would dominate a small project. ADR-003 already made v1 read-only.
- **Decision:** No write tool in v1. Finish and polish the read-only server first, then decide after Phase 4.
- **Consequences:** A smaller attack surface and simpler evals now. If a write tool is added later, it gets its own spec section, authorization design and ADR.

## ADR-012: MCP Inspector for manual inspection

- **Status:** Accepted (2026-11-22)
- **Context:** Tests exercise the server through a real MCP client, but there was no quick way for a person to try the tools, resource and prompt by hand. The official MCP Inspector gives a browser UI for that.
- **Decision:** Add `@modelcontextprotocol/inspector` as a dev dependency, pinned to an exact version, and a `pnpm inspector` script that runs the server from source with `tsx`. The Inspector's install script is explicitly disabled in `pnpm-workspace.yaml` (`allowBuilds`): it only installs client dependencies in a source checkout and does nothing when used as a dependency, and an unreviewed build script would otherwise fail `pnpm install` in CI.
- **Consequences:** Anyone can explore the server in a browser with one command. A new dev dependency tree to keep current. The version is pinned, so upgrades are deliberate. The Inspector is a manual tool and is not part of `pnpm check` or CI. Over stdio it runs locally and uses only synthetic data; remote HTTP inspection waits for Phase 4.

## ADR-013: Layered environment configuration, validated once

- **Status:** Accepted (2026-11-22)
- **Context:** Phase 2 adds a database URL, a way to choose between a local and a Docker Postgres, and later per-school tokens. These need one validated, typed place to read configuration, and an easy way to override values per environment (development, test, production) without copying every variable.
- **Decision:** `src/config` reads `.env`, then an optional `.env.<NODE_ENV>` that overrides it, then real environment variables, which always win. `NODE_ENV` comes from the real environment, defaults to `development`, and only selects the file. All variables are declared in one Zod schema (`src/config/schema.ts`) and validated together; a bad value fails with one message listing every problem and the files that were read. Empty values count as unset. `NODE_ENV` must be a plain name, because it becomes part of a file name. The loader uses Node's built-in `util.parseEnv` (no `dotenv` dependency), writes nothing to `process.env`, loads nothing at import time, and logs nothing (stdout carries the MCP protocol on stdio). `.env` files are never committed; `.env.example` documents them. CI and hosting platforms set variables directly. `pnpm test` sets `NODE_ENV=test` through `cross-env` so it also works on Windows.
- **Consequences:** Environment-specific files stay small. A deployment can override any file value without editing files. The behaviour is pure, so the tests inject the directory and environment. `util.parseEnv` is documented by Node but should be rechecked when the Node line changes. A new variable means one line in the schema.

## ADR-014: Postgres through `postgres` and Drizzle; one URL, a docker or local provider

- **Status:** Accepted (2026-11-22)
- **Context:** Phase 2 needs Postgres. Developers should be able to run the app against a Docker container or a Postgres installed on their machine (for example on Windows without Docker), and the rest of the code should not care which.
- **Decision:** Use the `postgres` (postgres.js) driver, and Drizzle ORM for the schema, migrations and queries from the schema slice onward. Not `node-postgres`. There is one `DATABASE_URL`. `DB_PROVIDER` (`docker` or `local`, default `docker`) selects which implementation of the `Database` interface is created: `DockerDatabase` or `LocalDatabase`. Both connect to the same URL. The difference is the guidance they give when the server cannot be reached: the docker provider points to `pnpm db:up`, the local one to the local server. Neither starts anything itself. `docker-compose.yml` maps the container to host port 15432, well away from the ports a locally installed Postgres usually takes (5432, and 5433 or 5434 for a second instance). A native Postgres on the same port answers first and rejects the container's credentials, which looks like a bad password. `check()` separates "cannot reach the server" from "the server rejected the connection" (bad password, missing database). No error message carries credentials. `DATABASE_URL` is optional in the config schema; `createDatabase` fails with a clear message when it is needed and missing.
- **Consequences:** The app, scripts and tests can run against either Postgres by changing two variables. The provider never starts Docker for you, which keeps it predictable and easy to test. Hosted Supabase (Phase 4) is just another `DATABASE_URL`. Drizzle and its migration tooling arrive with the schema slice.

## ADR-015: One throwaway database per test file, behind a test-mode guard

- **Status:** Accepted (2026-11-23)
- **Context:** Phase 2 tests need a real Postgres, and Vitest runs test files in parallel. Tests must not share state, and must never be able to touch a development or production database.
- **Decision:** A default test database (`rezen_mcp_test`, set through `DATABASE_URL` in `.env.test` or the CI environment) is the base. `createTestDatabase()` creates a fresh database named `<base>_<8 random hex characters>` on the same server and returns a `Database` connected to it; `close()` closes the pool and drops it. This works the same for the docker and the local provider, because it only uses the `Database` interface. Every helper first calls `assertTestMode`, which refuses unless `NODE_ENV` is `test` and the database name contains `test`. `pnpm test:db:setup` creates the base database if it is missing; it is idempotent, and `pnpm test` and `pnpm test:watch` run it first. `pnpm test:db:purge` drops every test database after a crashed run: the leftovers of exactly the form `<base>_<8 hex>`, then the base database itself (through the server's maintenance database, with connections forcibly closed). Nothing else is touched. The helpers live in `tests/support`, so they are not part of the production build. CI runs a Postgres service container with the base database.
- **Consequences:** Test files run in parallel without sharing state. `pnpm test` now needs a reachable Postgres, so CI and developers both need one (`pnpm db:up`, then `pnpm test` creates the base database). When none is reachable, `pnpm test` stops at the setup step with the connection hint, instead of failing test by test. Each file pays for creating a database; each database is empty and gets its schema from migrations once they exist (slice 4). A purge while tests are running would drop their databases, so run it only when no tests are running.

## ADR-016: Schema in Drizzle with generated migrations; `school_id` on every tenant table

- **Status:** Accepted (2026-11-23)
- **Context:** Phase 2 needs a persistent schema for the domain in `src/data/types.ts`, a repeatable way to apply it (developers, CI, every deploy), and a shape that makes school isolation easy to enforce and to prove.
- **Decision:** The schema is `src/db/schema.ts` (Drizzle). Migrations are SQL files generated from it by `drizzle-kit generate` (`pnpm db:generate`) into `drizzle/`, committed, and applied by `pnpm db:migrate`, which runs our own `migrateDatabase` through the `Database` interface rather than `drizzle-kit migrate`, so it uses the layered config and the docker or local provider hints. Tests apply the same migrations to each throwaway database. Tables: `schools`, `classes`, `students`, `subjects`, `terms`, `scores`. Ids are text, as in the domain types. A missing score is the absence of a row; a partly entered one has a null `ca` or `exam`. `ca` is checked 0 to 40 and `exam` 0 to 60 in the database as well as in code. `subjects` and `terms` carry a `position` for display and chronological order. `terms.is_current` marks the term in progress; a partial unique index allows at most one. `classes`, `students` and `scores` each carry `school_id`, and composite foreign keys (`students` to `classes`, `scores` to `students`, on id and school) make the school agree down the chain, so the database refuses a student or score filed under a different school than its parent. Foreign keys use the default no action, so nothing is deleted by cascade.
- **Consequences:** Row-level security (slice 10) can filter on one column of the row itself, with no joins, and cross-school mismatches cannot be stored. The cost is a redundant `school_id` on `students` and `scores`, which the seed and any future write path must fill in. The current term is global, not per school, which matches `Repository.getCurrentTerm()`; making it per school would change that interface. The database guarantees at most one current term, not at least one, so the Postgres repository must fail clearly when none is set. `drizzle-orm` is a runtime dependency and `drizzle-kit` a dev dependency (stable 0.45 and 0.31 lines, not the 1.0 beta). `drizzle/` is generated and excluded from Prettier; after changing `schema.ts`, run `pnpm db:generate` and commit the new migration. A test compares the tables and columns of a migrated database with `schema.ts`, so a forgotten migration fails CI.

## ADR-017: `DATABASE_URL` may map each provider to a URL (development and test only)

- **Status:** Accepted (2026-11-25). Extends ADR-013 and ADR-014; neither is superseded.
- **Context:** A developer often has both a Docker Postgres and a locally installed one, with different URLs. Changing `DB_PROVIDER` also meant editing `DATABASE_URL`, and the two were easy to get out of step.
- **Decision:** `DATABASE_URL` is either one postgres URL, as before, or a JSON object that maps providers to URLs: `DATABASE_URL='{"docker":"postgresql://…","local":"postgresql://…"}'`. This lives entirely in `src/config/schema.ts`: the variable is declared as a union of a URL and a partial record of provider to URL, and a `transform` on the schema reduces it to the one URL for `DB_PROVIDER`, so `Config.DATABASE_URL` is always a string (or unset) and nothing else changes, including `loadConfig`. An environment variable is a string, so a value starting with `{` is parsed as JSON first (`parseUrlMap` in `src/config/database-url.ts`); JSON that does not parse is left as it is and fails the URL check. Every URL, in either form, must be `postgres://` or `postgresql://`. Only `docker` and `local` are accepted as keys, and a map without a URL for the chosen provider is an error. The map form is **rejected when `NODE_ENV` is `production`**, which always needs a single URL. In an env file, wrap the JSON in single quotes (a double-quoted value with escapes does not work). Real environment variables still override files, and they replace the whole value. Messages never include the value, because it holds a password.
- **Consequences:** Both URLs can sit in `.env` or `.env.test`, and `DB_PROVIDER` alone switches between them. Production configuration is unchanged. A map missing the chosen provider fails at load even if nothing needs the database yet. Because Zod skips a `transform` when another field fails, a problem in `DATABASE_URL` that depends on `NODE_ENV` or `DB_PROVIDER` is only reported once those are valid, so in that rare case problems appear one round at a time rather than all together (ADR-013). An invalid entry inside a map is reported as `DATABASE_URL: Invalid URL` without saying which entry. The alternative, one variable per provider, was not chosen because it adds variables without removing the single resolved `DATABASE_URL`.

## ADR-018: An idempotent seed, run on every deploy by `pre-deploy`

- **Status:** Accepted (2026-11-25)
- **Context:** The Postgres repository and the isolation tests need the synthetic dataset (two schools) in a database, and a deployment must be able to set one up the same way every time without a person deciding whether it already has data.
- **Decision:** `seedDatabase` (`src/db/seed.ts`, run by `pnpm db:seed`) inserts the dataset from `generateDataset()` into an already migrated database. Every insert is insert-or-ignore on the primary key, so a second run changes nothing, a row that exists is never overwritten, and nothing is ever deleted or truncated. Tables are filled parents first, in one transaction, so a failed run leaves the database as it found it. `school_id` on students and scores is taken from their class (ADR-016). Terms are inserted as not current, and the dataset's current term is marked current only if no term is yet, so a re-run never moves a current term that was advanced (and the one-current-term index cannot block the other terms). `pnpm pre-deploy` runs `pnpm db:migrate` and then `pnpm db:seed`; the name has a hyphen because npm and pnpm run a script called `predeploy` only before a script called `deploy`. The existing `pnpm seed` still only prints a summary and touches no database. Seeding before migrating fails with a `not-migrated` `DatabaseError` that says to run `pnpm db:migrate`. Errors from a failed seed carry the database's own message and SQLSTATE, not Drizzle's message, which repeats the row values.
- **Consequences:** Running it on every deploy is safe, and so is running it by hand. Because rows are never updated, a change to the generated dataset (another seed or a new field) does not reach a database that is already seeded; reset such a database to pick it up (this is deliberate: nothing here may destroy data that someone changed). Seeding production with synthetic data is acceptable only because this project has no real data (ADR-001). Per-school tokens (slice 7) will need the same insert-or-ignore treatment.

## ADR-019: `PostgresRepository` and a `DATA_STORE` switch; one defined order for every list

- **Status:** Accepted (2026-11-25)
- **Context:** ADR-004 promised a Postgres implementation of `Repository` that passes the same contract tests as the in-memory one. The in-memory lists came back in the dataset's insertion order, which Postgres does not keep: without an `ORDER BY` a query may return rows in any order, and a text ordering also depends on the collation the database was created with. Tools such as `get_class_results` list unranked students in the order the repository gives them, so an unstable order would give different answers from the same data.
- **Decision:** `PostgresRepository` (`src/db/postgres-repository.ts`) implements `Repository` with Drizzle over a `Database` (ADR-014). It does not own the `Database`; whoever created it closes it. Every list has one defined order, written on the `Repository` interface and used by both implementations: classes by level then ID; students by name then ID; scores by student ID then subject; subjects and terms by their `position`. Text is compared by its bytes: `collate "C"` in Postgres, and `compareBytewise` (a plain code-unit comparison) in memory, so the order does not depend on the database's locale. `InMemoryRepository` now sorts students and scores to match (its students used to come in insertion order). An unknown ID gives `undefined` or `[]`, as before. `getCurrentTerm()` reads the term whose `is_current` is true and throws a `DatabaseError` of kind `no-current-term` when there is none (ADR-016 allows at most one, not at least one), with a message that says to run `pnpm db:seed`. The contract is one function, `describeRepositoryContract` (`tests/support/repository-contract.ts`), whose expected answers are worked out from the dataset, never from the implementation. It runs against both implementations on three datasets (hand-built edge cases, the synthetic dataset, and the edge cases with the first term current). A separate test calls every tool through a real MCP client on both stores and requires identical results. `DATA_STORE` (`memory` or `postgres`, default `memory`) chooses the store; `openDataStore` (`src/data/store.ts`) builds it. For Postgres it checks the connection and reads the current term at startup, so an unreachable server, a database with no tables, and one with no current term each stop the server with a message that says what to do, instead of failing on the first tool call. The stdio entry point closes the pool when the client disconnects or the process is stopped, because an open pool keeps Node alive.
- **Consequences:** The same server can run on either store, and the tests prove they agree. The default stays `memory`, so `pnpm dev` and the Inspector still need no database. Changing the order of a list is a change to the contract and must update both implementations and the contract test together. The in-memory order change is visible: unranked students now come back sorted by name instead of in insertion order. Until per-school tokens arrive (slices 7 to 9), the tools still take `schoolId` from the caller, so with `DATA_STORE=postgres` any caller can read any school; that is acceptable only because the data is synthetic and the server runs locally over stdio. `findSqlError` moved from `src/db/seed.ts` to `src/db/errors.ts` so the seed and the startup check share it.

## ADR-020: Per-school tokens, stored only as hashes, issued by a command and never seeded

- **Status:** Accepted (2026-11-25)
- **Context:** The spec promises one token per school, with the school derived from the token (slice 9) and row-level security behind it (slice 10). Before the server can use tokens, there must be a way to make them, check them and revoke them, and a way to store them that does not turn a leaked copy of the database into a set of working credentials.
- **Decision:** A token is `rzn_` followed by 32 random bytes from the system's random source, base64url-encoded without padding (47 characters). It carries no school, date or other meaning. The table `school_tokens` (`src/db/schema.ts`) holds a row per token: an id (a UUID, used to list and revoke), the school, the lowercase hex SHA-256 of the token, an optional label of at most 100 characters, the creation time and a revocation time. The token itself is never stored. A check constraint accepts only 64 lowercase hex characters in `token_hash`, so a plaintext token cannot be stored by mistake, and the hash is unique. A plain SHA-256 is enough because the input is 256 random bits and cannot be guessed; a slow password hash would add cost and no safety. `TokenStore` (`src/auth`) has four operations: `issue`, which returns the plaintext once; `verify`, which returns the school and token id, or `undefined`; `revoke`, which sets the revocation time; and `list`, which never returns a token or a hash. `verify` answers `undefined` in the same way for a malformed, unknown and revoked token, so a caller learns nothing about tokens that exist, and a malformed value never reaches the database. A school may have several tokens at once, so one can be replaced without a gap. Revoking keeps the row, and only the first revocation time is kept. Tokens do not expire in v1. `pnpm db:token issue <schoolId> [--label text]`, `list [--school id]` and `revoke <tokenId>` run these against the database the app uses. **Seeding never creates tokens**: a token made by the seed would have to be the same in every database, or be printed by a deploy, and either way it would be a credential that is known in advance. This replaces the expectation in ADR-018 that tokens would be seeded with insert-or-ignore.
- **Consequences:** A copy of the database, a backup or a log of its rows cannot be used to sign in. A lost token cannot be recovered: issue a new one and revoke the old one. There is no expiry or automatic rotation; a token works until someone revokes it. The plaintext is shown once, in the terminal that ran `pnpm db:token issue`, so it should be copied to wherever it is needed and not pasted into chats, tickets or the repository. Tests make their own tokens in a throwaway database, so no token appears in the repository, which keeps ADR-001's rule that there are no secrets in it. Nothing in the server uses tokens yet: slice 8 builds a school-scoped repository, and slice 9 makes the server derive the school from a token and removes `schoolId` from tool inputs. The in-memory store has no tokens; slice 9 decides how a server on `DATA_STORE=memory` identifies its school. `verify` runs with full access to `school_tokens`, because it runs before anyone is identified; slice 10 must make sure the database role that serves tool queries cannot read this table. Tokens are looked up by their hash with an index, which does not give an attacker a usable timing signal, because the hash of a guess says nothing about the hash of a real token. Labels are for people and are shown by `list`, so they must not hold secrets or personal data.
